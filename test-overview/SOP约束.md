# SOP 约束

本文约束 software-test-sop 自身。执行测试时不用读；改任何 skill、模板、verify 样例前必须读。

## 1. 只写通用流程

| 层 | 放什么 | 位置 | 换项目时 |
|----|--------|------|---------|
| skill | 步骤、出口、门禁、取样规则、模板骨架 | `software-test-sop/test-*` | 不改 |
| 测试手册 | 基址、鉴权菜谱、信封、角色、探活、参照 | `artifacts/_project/T0-01-测试手册.md` | 重建一份 |
| 需求产物 | 本需求 AC、接口卡、cases、结果、BUG | `artifacts/{需求}-qa/` | 不复用 |

- skill 里不出现项目或需求专有内容：仓名、服务名、真实 URL、表名、需求编号、业务独有规则。举例只用占位符：`{BASE}`、`{svc}`、`{角色}`。
- 某个需求踩到的坑：换项目还会发生 → 写成通用规则；否则回填手册，不进 skill。

## 2. 篇幅上限

| 对象 | 上限 |
|------|------|
| 每个 `SKILL.md` | 120 行 |
| 其他 `.md`（总纲、模板） | 200 行 |
| 全部 `.md` 合计（不含 README） | 1000 行 |
| verify 样例脚本（每个 `run.*`） | 80 行 |

超了只能删或合并，不能拆新文件绕过。

## 3. 增删规则

1. 加规则前依次试：做成模板字段或表头 → 并进已有规则。都不行才加一句话。  
2. 新增须对应真实问题（试点或复盘），写在变更说明，不写进正文。  
3. 一条规则只写一处，其他地方写「见 生命周期 › {标题}」。  
4. 禁止补丁式写法：带日期的修订说明、「再次强调」、同一意思重复。  
5. 被模板吸收的规则从正文删掉。

## 4. 与 development-sop 的边界

- **不依赖**开发 SOP 产物；接包最小集自洽。  
- **不修改** development-sop 仓内文件。  
- 缺陷契约用 T3 自有字段；**不使用**开发 S3 的 A/B/C/D 分类。  
- 若同仓并存两套 skill，靠 name/description 区分；测试会话只加载 `test-*`。

## 5. verify 硬约束

- `cases.json` **只引用** T1-04 已有字段（path、headers 变量名、body 键）；禁止卡外路径。  
- `env.local` / `out.txt` 不入库（见根 `.gitignore`）。  
- 样例 AC/路径须虚构；禁止把试点真实 path 写进 skill 仓。
